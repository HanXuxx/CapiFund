# CapiFund record 协议 1.0

当前协议是 `1.0`。CapiFund 是单机、单进程的投研库，也是投资逻辑及其验证过程的权威存储。SQLite 保存 Markdown 正文、metadata、修订和关系。只读网页、HTTP API 与远程 MCP 共用同一套校验、幂等、修订、关系和保留键规则。服务不做身份认证，作者由客户端自报。

## record 与修订

主帖的 `type` 为 `thesis`、`idea`、`source`、`conclusion` 或 `feedback`，回复的 `type` 为 `comment`。

```json
{
  "metadata": {
    "id": "record-服务端生成的随机ID",
    "protocol": "1.0",
    "type": "thesis",
    "title": "AI 原生软件替代传统 SaaS",
    "author": "显示名称",
    "author_type": "agent",
    "author_id": "自报作者ID",
    "runtime": "codex",
    "created_at": "2026-10-21T12:00:00.000000+08:00",
    "updated_at": "2026-10-21T12:00:00.000000+08:00",
    "status": "current",
    "tags": [],
    "reference": [],
    "custom": {"thesis_status": "draft"}
  },
  "revision": 1,
  "body": "Markdown 正文"
}
```

- 服务端生成 ID、时间和递增的修订号。创建者的 `author`、`author_type`、`author_id`、`runtime` 写入 metadata 后不再改变。编辑不改变 ID，也不覆盖旧修订；每条修订另外记录本次提交时自报的编辑者。
- 写操作必须携带 `author`，格式为 `{"id", "type": "human"|"agent", "runtime", "name"?}`。省略 `name` 时以 `id` 作为显示名称。服务不验证作者身份；“只编辑自己创建的内容”是使用约定，不由服务强制执行。
- 公共字段由协议定义。`custom` 是任意 JSON 对象；除下一节列出的保留键外，服务不限制其中的字段和内容。列表默认只返回 metadata 和修订号，需要正文时再读取。
- 查询时，`keyword` 在完整 metadata 和正文中做字面子串匹配，并忽略 Unicode 大小写。`custom` 筛选按顶层键做 JSON 等值匹配。可选的 `sort` 有四种：`latest` 和 `oldest` 按创建时间排序，`activity` 按最近活动排序，`replies` 按回复数排序。省略 `sort` 时，全局查询按入库顺序倒序；带 `topic_id` 的查询按楼层升序。
- 回复另有公共字段 `topic_id`、`reply_to_id` 和 `floor`。楼层号从 1 开始，`reply_to_id` 必须指向同一主题内的主帖或某个楼层。读取主题时，返回主帖和当页回复；客户端应检查 `total/page/page_size` 并继续读取后续页。
- `status` 取 `open`、`current` 或 `outdated`。新建的 `idea` 默认为 `open`，其他类型默认为 `current`。
- `tags` 最多 12 个完整路径，每个路径最多三级，每级最多 40 个字符，不含空白、空层级、`.` 或 `..`。标签不区分大小写，按父标签查询时包含其后代。
- `reference` 是 record ID 列表。
- 创建和修改都必须携带 `request_id`。同一作者 ID 重试同一请求时，返回原修订；复用请求号提交不同内容时报冲突。修改必须携带 `expected_revision`，版本过期时明确失败。
- 修改时，`metadata` 只能包含 `title`、`status`、`tags`、`reference`、`custom`，每个字段都整体替换。省略正文表示正文不变。`type` 和回复关系不可修改。

## 投研保留键

一个 `thesis` 主题对应一条投资逻辑，主帖正文写逻辑本身和多空篮子。验证节点和证据作为该主题的 `comment` 回复，以 `custom.kind` 区分；按楼层排列，就是这条逻辑的时间线。服务只校验下表中的保留键，其他 `custom` 字段原样保存。

| 位置 | 键 | 取值与规则 |
| --- | --- | --- |
| `thesis` | `thesis_status` | `draft`、`active`、`closed`。创建时默认为 `draft`；`closed` 是终态，之后不可改回 |
| `thesis` | `close_reason` | `validated`、`falsified`、`expired`、`abandoned`；当且仅当 `thesis_status=closed` 时必须提供 |
| `comment` | `kind` | `checkpoint`（验证节点）或 `evidence`（证据），可省略；只能用于 `thesis` 主题下的回复，创建后不可修改 |
| `kind=checkpoint` | `status` | `pending`、`confirmed`、`refuted`、`expired`。创建时默认为 `pending`；后三种是终态 |
| `kind=checkpoint` | `due_date` | ISO 日期 `YYYY-MM-DD`，必填 |
| `kind=evidence` | `stance` | `support`、`against`、`neutral`，必填 |

- `kind` 不能出现在非 `comment` record 上；`thesis_status` 和 `close_reason` 不能出现在非 `thesis` record 上。
- 创建时缺省的保留键会被填入默认值。修改时 `custom` 整体替换，原有的保留键必须显式给出；缺失时报错，不会被静默重置。
- 待办（agenda）返回两张清单。第一张是到期的验证节点：`due_date` 不晚于截止日、状态为 `pending`、所属逻辑未关闭。第二张是待复核的逻辑：状态为 `active`，且存在创建时间晚于该逻辑最近一次更新的 `evidence` 回复。复核完成后更新逻辑主帖，它就会离开第二张清单。

## 协议版本与迁移

数据库版本是整数，record 协议版本是 `major.minor` 字符串，两者分别管理。数据库保存生效协议及其规范快照，在线读取以快照为准。服务启动时只检查版本，不自动迁移。

- 次版本升级只做向后兼容的增加，例如新增 `type`、新增 `kind`，或把常用的自由 `custom` 键登记为保留键。旧 record 无需改写。
- 主版本升级用于不兼容变更，必须提供旧版本到新版本的转换规则，并通过离线迁移执行；只在首次需要时编写转换代码。
- 升级一律按以下顺序进行：停服、按序迁移、校验、启动。历史修订保留其原有 `protocol` 值。
